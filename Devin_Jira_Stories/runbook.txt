
Jira → Devin Automation Runbook
Smart Hospital &amp; Patient Management System  ·  as of 16 Oct 2026
Creating a Task in Jira project UST-HealthCare (KAN) automatically starts a Devin session that analyses the ticket, builds the microservice, runs tests and opens a pull request on Msocial123/UST-HealthCare-Project. This runbook explains how that works, every setting involved, and how to test and troubleshoot it.
1. How it works
One Jira event drives the whole run: the automation turns &quot;issue created in KAN&quot; into a Devin session, and the session ends with a pull request a human reviews.

The highlighted box is the only part you configure per project; steps 1–2 and 5–6 depend on the one-time connections in section 3.

3. One-time setup checklist
All of these must be true before a ticket can trigger a working session; every item is already done for KAN.
Devin for Jira app installed in Jira, and the site linked to Devin (Jira → Apps → Devin shows connected).
Devin → Settings → Connections → Jira shows Connected (admin account muralik1403).
Atlassian account linked to your Devin user — profile → Settings → Connections → Atlassian shows &quot;Unlink user&quot;. Required because the Devin and Jira logins use different emails; without it the Issue created trigger cannot be saved.
GitHub connected — Settings → Connections → GitHub shows @Msocial123 with UST-HealthCare-Project in its Repositories list.
GitHub Automation scope = All connected repos — GitHub connection → General. The repo is public; with &quot;Private repos only&quot; sessions got git 403 and could not push.
Playbook saved — listed under Active playbooks, macro !smart_hospital__analyze_plan__build.
Session mode = Direct session creation ON (Jira connection page), so Devin builds instead of only posting a scoping comment.
One automation only — the old label-based rule (label + status Done) was deleted so a ticket never starts two sessions.

5. Playbook
Name: Smart Hospital — Analyze, Plan &amp; Build (default playbook).
Macro: !smart_hospital__analyze_plan__build (double underscores). The older label !smart_hospital_analyze_plan_build does not match it.
Attached by: the macro as the first word of the automation&apos;s Instructions (there is no Playbook field on this automation type).
Workflow: read ticket → read README and AGENTS.md → analyse → plan → implement only the scope → tests → run and fix → review diff → report.
Guardrails: Python 3.12+, FastAPI, Pydantic v2; synthetic data; no secrets; no Docker, Kubernetes, frontend or CI/CD unless asked; acceptance criteria are the checklist.
6. Writing a Jira story that works
A ticket triggers on creation, so it must be complete when you click Create. Use the per-service story documents that accompany this runbook.
Project / type: UST-HealthCare (KAN), Task.
Summary: &lt;Service name&gt; - Endpoints, Tests and Pull-Request Readiness.
Labels and Assignee: leave empty — a playbook label or assigning Devin can start a second session.
Description: Objective, Part 1 Analysis and Plan, Part 2 Build, Part 3 Endpoints, Part 4 Tests, Part 5 PR Readiness, Scope and Constraints, Acceptance Criteria.
Do not create test or placeholder tickets in KAN — each one starts a paid session.

9. Webinar demo script
Architecture (1 min) — eight-service diagram; Identity built, Patient and Provider built by Devin from Jira.
Settings tour (3 min) — Jira connection page → Automations → Edit (trigger, macro, Jira tool, network) → GitHub Automation scope.
Create the ticket live (2 min) — paste the prepared story; no label; Create.
Show the trigger (1–2 min) — refresh Events until &quot;Created KAN-n&quot; appears; open View session; point out &quot;Used playbook&quot;.
Watch Devin start (2 min) — reads AGENTS.md, builds a task list, posts the plan.
Show a finished result (3 min) — PR #3 or #4: files, tests, README, completion report; Jira ticket with PR link.
Close (1 min) — humans review and merge; guardrails from AGENTS.md and the playbook.
